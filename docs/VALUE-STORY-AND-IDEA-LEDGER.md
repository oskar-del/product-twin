## The core pitch (for presentation / landing page)
People pay architect offices for exactly the things buyers never see and rarely think about: does sewage fall correctly, where does the electrical service enter, will the roof carry snow, does the design pass BBR/CTE, what does it actually cost to build, can the products actually be delivered here. **We make all of that visible, checkable and costed — before an architect is even hired.** Not architecture images: buildable confidence.
- Plot intelligence: real parcel, terrain, sun, measured views (viewshed), geology/flood/heritage screens — evidence-receipted (Svärtinge 54:28 = worked example, 20 official source receipts).
- Design with systems already proposed: massing + water/sewage/electric/heating/ventilation skeleton + pass/fail vs rules + parts list.
- Progressive disclosure: buyer sees five green rows + one price; architect lens sees runs/falls/loads; procurement lens sees BoM with live offers. One graph, three doors.
- Every claim carries its evidence class — the honesty UI (AUTHORITATIVE/INDICATIVE/DERIVED/REPORTED/CONCEPT) is a feature customers can see, not internal hygiene.

## Truth law for systems content (Oskar, 2026-08-18 — NON-NEGOTIABLE)
If we render pipes/wires/systems, what we show must be TRUE per an executable rulebook — never model-recalled "knowledge".
1. Per-domain RULEBOOKS AS CODE: dedicated deep-research agents distill authority sources (BBR chapters, Säker Vatten, SS 436-series el, CTE DB-HS/HE, kommunal VA praxis) into requirement engines with citation + version + date per rule. CANOPUS pool/structural engines = the pattern.
2. LLM proposes, SCRIPT verifies: design generation may be model-driven; compliance/pass-fail is always a deterministic gate. A model may never waive or invent a rule at runtime.
3. Mutation-tested: every rulebook ships with deliberate-failure fixtures (like the Svärtinge validators).
4. Professional boundary: we PROPOSE + CHECK; certified engineers/architects SIGN. Never present output as stamped engineering.
